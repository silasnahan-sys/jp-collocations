## 1. CRITICAL — the Hyogen scraper has never worked, and fails silently

Measured: fetched `https://collocation.hyogen.info/word/風` (698 KB, HTTP 200)
and ran `HyogenScraper.parseHtml` verbatim against the real bytes.

| | |
|---|---|
| entries the parser produced | **10** |
| what those 10 are | `風あ` `風か` `風さ` `風た` `風な` `風は` `風ま` `風や` `風ら` `風わ` |
| what they actually are | the **あかさたなはまやらわ kana index nav-bar** at the page foot |
| POS assigned to all 10 | 動詞 — because a layout `<tr>` contained the substring 動詞 |
| reading extracted | `""` |
| **collocations actually on the page** | **10,411** |

The parser looks for `<tr>/<td>`. The page's 17 `<tr>` are all chrome — header,
sidebar, ads, kana index. The real data is in a completely different shape:

```html
<div class="col_font1">名詞</div>                     ← POS section
<div class="col_midasi1"><b>～ 風</b>[名詞]1</div>      ← direction + sense
<div class="font8">声は風の　　憑り風に　　なだれの風　…</div>  ← items, split on 　　(U+3000 ×2)
```

Correct extraction against the same bytes yields 6,910 + 515 + 2,986 items
across three sections (`～風` sense 1, `～風` sense 2, 複合名詞).

Two further bugs that will bite the moment the selector is fixed:

1. **Double headword.** Hyogen's items are already *full phrases* containing the
   headword (`風が吹く`, not `が吹く`). The code does
   `fullPhrase: headword + collocate` → `風風が吹く`. The field to populate is
   `fullPhrase` directly; `collocate` must be *derived* by removing the headword.
2. **Direction is dropped.** `風 ～` (headword-initial) and `～ 風`
   (headword-final) are different collocational facts and the current model has
   nowhere to put the distinction. `col_midasi1` carries it; parse it into
   `pattern`.

Why nobody caught it: the scraper **returns 10 entries and no error**. It reads
as a working feature with a thin corpus. This is the most dangerous failure shape
there is, and it argues for a golden test that pins a byte-fixture of a real
Hyogen page — the same discipline `golden/plex.mjs` already applies to Plex.

Your 220 seed entries are hand-authored and clean (`collocate: "が吹く"`, real
example sentences); they are labelled `source: "hyogen.info"` but did not come
from this code path. The scraper's output has never entered your corpus. **You
lost nothing — you just never gained anything.**

## 2. CRITICAL — the TWC scraper is broken *and* the corpus forbids what it does

### It cannot work as written

`acceptTerms()` POSTs `accept=true` to `/search/`. The real gate is **client-side
JavaScript**:

```js
function agree() {
  if ($("#checkbox_agree").is(':checked')) {
    $.cookie("agreed","true", { expires:date });   // ← 1-year cookie
    location.href = "/search/";
  }
}
```

There is no form POST to make. Measured: the URL the scraper fetches returns the
**6,587-byte terms page**, zero `<table>`, zero `<tr>`; the scraper's
`<table class="result|colloc|profile">` regex matches **0** times.

Sending `Cookie: agreed=true` does clear the gate (verified — HTTP 200, gate text
gone). But the page behind it is `NINJAL-LWP for TWC`, a **jqGrid single-page
app**: results arrive by AJAX into a JS grid. There is no server-rendered table
to scrape at any URL the current code knows, and `?q=…&options=exact` is not the
query format the grid uses.

### It should not work

From the gate's own 利用規約, §2「許諾の範囲等」:

> （２）NLTの検索結果の複製を禁じます。

Reproduction of NLT search results is **prohibited**. The scraper's entire
purpose is to copy search results into a persistent local lexicon that the plugin
then exports to JSON and that ships from a public GitHub repo. That is squarely
the prohibited act — and §2(1) additionally limits use to 研究・教育目的.

**Recommendation: delete the TWC scraper rather than repair it.** Fixing it means
building a working circumvention of a consent gate in order to do the one thing
the consent text forbids. The settings toggle, the two commands, the rate-limit
slider and the `twc`/`twc-pattern:` tags should go with it.

If you want TWC's frequency signal, the legitimate roads are: use the site by
hand under its terms and record findings as your own notes, or ask NINJAL/Lago
about the 商業利用は別途ご相談 clause — they do license it. Neither is something
the plugin should automate.

Hyogen, by contrast, publishes no terms-of-use, 転載 or 著作権 restriction on its
pages, and is derived from 青空文庫 (public-domain). Scraping it politely — which
the existing 2 s rate limit already does — is a materially different situation.
**Fix Hyogen; retire TWC.**

## 3. HIGH — two search engines, two answers, one product

| surface | engine | matching |
|---|---|---|
| `CollocationView` (sidebar), `SearchModal` | `SearchEngine` | normalize → kana-fold → romaji → grammar expansion → wildcard → **Levenshtein** |
| `LexiconPanel` (the unified surface) | `unifiedSearch` | `norm()` = NFC + strip space + lowercase, then exact / prefix / includes |

`unifiedSearch` has **no kana folding, no romaji, no fuzzy, no wildcard**. So
`kaze` finds 風 in one box and nothing in the other; `かぜ` vs `カゼ` behave
differently; the two boxes rank the same corpus by incomparable scores
(`80 + 20` boosts vs `100 / 70 / 45` tiers). For a tool whose whole promise is
"type it however it comes to mind and find it," having the newer, more prominent
surface be the *less* capable matcher is the single worst ergonomics fact in the
plugin.

**Fix: extract one `matchJapanese(query, fields) → score` module.** Both call it.
Kana folding, romaji, wildcard and the grammar expansion live there once.

### And the fuzzy path does not scale

`scoreEntry` runs, per entry, per field, per term, a **sliding-window Levenshtein
over every substring offset**. Benchmarked (Node 24, this machine):

| entries | ms per keystroke |
|---|---|
| 220 (today) | 16 |
| 2,000 | 100 |
| 10,000 | 505 |
| 50,000 | **2,533** |

Main thread, behind a 90 ms debounce; mobile is roughly 3–4× slower. Today's
corpus is fine. But §1 shows **one Hyogen word is 10,411 collocations**, and
`concordance.mjs` is explicitly designed to pour marker instances into
`PatternStore` at corpus scale. You are one successful scrape away from a
2-second-per-keystroke search box.

**Fix, in order:** (a) cheap prefilter — skip Levenshtein unless the field shares
a bigram with the query; (b) precompute `normalizeJapanese`/`toHiragana` per entry
at store-load, not per keystroke (currently recomputed for every field of every
entry on every keystroke); (c) cap fuzzy to the top N by cheap score. (a)+(b) are
each a few lines and together are worth well over an order of magnitude.

## 4. HIGH — the Plex road dead-ends one step before the pipeline

`src/notes/plex.ts` is the best-engineered file in the project: pure, golden-
tested, adapter-isolated, tolerant parsing, and `explainPlexTransportError` /
`isLanAddress` correctly distinguish "you are on a different Wi-Fi" from "your
token is wrong" — a failure mode most software never bothers to separate.
Subtitle picking correctly de-prioritises `forced` tracks and refuses image
codecs *loudly*. Very little to improve here.

The gap is at the seam. `writeTranscriptNote()` produces a **transcript** note.
`runFullPipeline()` (⚡) requires a **capture** note whose frontmatter carries
`sources: [[transcript]]`. The bridge between them, `newCaptureNote()`, is
hard-wired to YouTube:

```ts
const hist = ...filter(f => f.basename.startsWith("_watch-history"))...
const ids = [...md.matchAll(/youtu\.be\/([\w-]{11})/g)]
```

A Plex transcript has `plex_rating_key` / `plex_part_key` frontmatter and no
YouTube id, so it can never be reached. **After a Plex transcript is created, the
user must hand-write a capture note to use ⚡ on it.** The YouTube road has a
one-command bridge; the Plex road has none.

**Fix (small, highest value/effort ratio in this document): a
`capture-note-from-active-transcript` command** — take the open transcript,
create `Capture {title}.md` with `sources: [[it]]` prefilled, open it. Source-
agnostic, so it serves Plex, jimaku, YouTube and hand-pasted `.srt` equally.
This is the difference between "Plex support" and "Plex support that reaches the
product."

Second, smaller: `writeTranscriptNote` disambiguates collisions with an
`HH:MM` suffix, so re-transcribing the same episode twice in one minute still
collides. Use the ratingKey.

## 5. MEDIUM — cross-platform is *correct* but the surface count is the problem

Platform gating is genuinely well done: 9 `Platform.isDesktopApp` guards, each
refusing with a specific Japanese Notice rather than no-opping; `FileSystemAdapter`
checked before every Node path; `nodeRuntimeAvailable()` before ffmpeg/yt-dlp;

false` in the manifest is honest.

The ergonomic problem is different: **nine registered views** (tray, follow,
collocations, dictionary, X, recon library, review, pipeline, discourse mode)
plus modals, in one plugin. Add the two search boxes from §3 and the answer to
"where do I type a word to see what I know about it?" is genuinely ambiguous. The
architecture is sound; the *entry points* have accreted. Before adding anything,
the highest-value UX work is deciding which single surface is the front door and
demoting the rest to panels within it.

## 6. THE PARSER — what it will actually take

### 6.1 What is actually true today

All goldens green, verified by running them: scoreboard 48/48, calculus-turns
33/33, calculus-corpus 18/18, calculus-precision 29/29, components 25/25,

The July trajectory was honest and is worth restating because it is the reason

fail branch and built the move concordance instead of relitigating. That is a
project that can be wrong on purpose. Very few can.

### 6.2 The diagnosis: you already answered the parser question. Twice.

The question "can this ever be a parser?" has been answered by measurement, and
the answer is recorded in two places you wrote:

- **DESIGN §23** decomposes the problem into four layers and assigns each to
  whoever can actually answer it: (1) turns → diarization for audio, humble
  defaults for text; (2) **components** — echo / aizuchi / reaction / return /
  connective / quotative / fragment — *"the parser's honest ceiling today — and
  it's USEFUL"*; (3) relations → **drawn by hand**; (4) readings → **human,
  plural**.
- **DISCOURSE-VERDICT §12** measured the fail and demoted the move label to
  bookkeeping, making the **marker instance** the unit.

Both say the same thing: **layer 2 is the parser, and layers 3–4 are not.** So
"true parserhood" is not a further distance to travel. It is a *smaller claim to
make well* — and the machine is already capable of making it.

Here is the sharp version. `golden/concordance.mjs`, run this session, prints:

```
position overall: final 31 / clausal 71 / medial 798  →  97% are NOT turn-final
```

97% of real interactional-marker instances are *not* in the canonical turn-final
slot. A parser that types moves must resolve every one of those from context it
does not have. A concordance that reports *"this marker occurred here, in this
position, in this turn, at this timestamp"* is **correct for all 900** — because
that claim is a substring plus a position test, and both are decidable from
skeleton alone. The ceiling is not low. The claim was too big.

### 6.4 What "parserhood" should be redefined as — and the honest ceiling

Stop asking for a discourse parser. Ship a **component parser + move
concordance**, and let the board be private bookkeeping that is never quoted:

| layer | claim | who | status |
|---|---|---|---|
| 1 turns | who spoke, where | diarization (audio) / given (hand) | text-guessed 94% — **fix with audio** |
| 2 components | echo / aizuchi / reaction / connective / quotative / fragment | **machine, precision-first** | **built, green, unwired** |
| 2.5 concordance | *this marker, this position, this turn, this timestamp* | machine | **built, green, shipping** |
| 3 relations | what points at what | **hand** | machine-by-recency — demote |
| 4 readings | move name, tone | **human, plural** | machine single-label — demote to hint |

That product is defensible on every row, it is most of the way built, and it is
what a learner actually needs: not "the machine told me this was a CONSCRIPT,"
but "じゃないですか occurred 54 times in this episode; here are all of them with
their positions and what followed each." §12 already measured that asset:
imiron じゃないですか 7→54, ですよね 3→66, よね 0→60, じゃん 0→11.

### 6.6 The missing layer, named mechanically

The standing intuition on this project has been that *something is structurally
missing* — and that saying so keeps producing misdirection, because "a layer is
missing" invites people to add theory, and theory here means more operators.
With the drill fixed, the gap can be stated as a count instead of a feeling.

Primitive census over both fixtures (1,344 turns, 2,206 moves):

| primitive | nenko | imiron | |
|---|---|---|---|
| PROPOSE | 160 | 593 | the noise floor |
| CONSCRIPT | 52 | 217 | **the one productive channel** |
| ADJUST_FORCE / ACKNOWLEDGE / PREFACE | 148 | 492 | hedges and grounding |
| ASSERT_AS_DERIVED / RELATE_SUPPORT | 76 | 184 | monologic |
| **RELATE_CONTRAST** | 6 | **3** | |
| **GRANT** | 6 | **1** | |
| **REJECT** | **0** | **0** | |
| **RE_TYPE** | 1 | 2 | |
| **DENY_COMMITMENT** | **1** | **0** | |
| SHELVE / RESUME QUD | 1 / 0 | 1 / 1 | |

Two facts fall out, and neither is about linguistics.

**One.** Across three hours of a two-host *debate* podcast, the entire relational
half of the algebra — the part that makes this an argument model rather than a
marker counter — fires **7 times in 1,042 turns**. REJECT is zero over both
files. The project's flagship result, the DENY_COMMITMENT at [07:50], is a
population of one.

**Two.** 47–48% of turns carry nothing but PROPOSE, ACKNOWLEDGE or a hedge.

Now the mechanism. Every relational primitive binds through
`mostRecentTable(board, speaker, 'other')` — "the other speaker's most recent
live proposition." That requires knowing who spoke, and §6.3(3) measured that
`R4:floor-continues` decides 984 of 1,042 turns. So "the other speaker" is
usually a guess dozens of turns stale, and a primitive that binds to it cannot
fire correctly even when the surface evidence is perfect.

So the missing layers are not missing *theory*. They are the two layers DESIGN
§23 specified and the calculus skipped on its way to layers 3–4:

- **Layer 1 — who is speaking.** Guessed from text at a 94% default rate. Every
  relational move is downstream of it. This is a *signal* problem: for local
  audio, diarization answers it and text never will.
- **Layer 2 — components** (echo / reaction / return / fragment / connective /
  quotative). These are precisely the skeletal signals that say *this turn is
  responding to that one* — the input relations need in order to bind on
  something other than recency. `components.ts` is built, green at 25/25, and
  imported by nothing.

**This is the direct answer to the skepticism about feeding in more of your own
data.** Ratifying CONSCRIPT firings ✓✕ improves precision on the one channel
that already works. It cannot make REJECT fire, because REJECT is not failing
for want of labels — it is failing because nothing tells the system which prior
proposition a turn is answering. A learned classifier trained on that gold would
fit the CONSCRIPT channel and the floor-continues default, and would measure the
size of those two bugs.

That is also why past attempts to name this went sideways: "missing layer" was
heard as "we need a richer account of Japanese," and the answer was more
operators. The actual missing inputs are one audio pipeline you already have and
one module you already wrote.

**Order that follows from this:** wire layer 2, put diarization under layer 1,
and only then ratify — because only then is there more than one channel whose
precision is worth measuring. The drill is now the instrument that will say
whether it worked: if the board starts doing real discriminative work, the gap
between `marginal` and a learner's score will open. Today it is ~2 points.

### 6.5 The real bottleneck is not the parser

`golden/precision/samples.jsonl` holds 112 rows. **Zero are ratified** — after
three days in July and a further week since. Every precision number this project
has ever produced is the model grading its own output.

Ratification-as-homework has never completed, and it never will, because it is a
separate chore with no reward. It has to become a **byproduct of study**: each
drill answer, each board review, each 談話モード boundary tap silently emits one
✓✕. Until that exists, no amount of parser work can be *evaluated*, and the
project will keep re-deriving the same three findings because there is no
mechanism for a finding to become settled.

**This is the single highest-leverage build in the entire plugin**, and it is a
UX problem, not a linguistics one.

## 6.7 INGEST — the one-stop-shop question

The goal stated 2026-08-01: *everything noticed in a day, in any form, through
one door, handled the way its medium deserves, reconciled, and out the other
side as study material.*

The doors already exist. Measured — 60 registered commands, of which the ingest
set is: 🎙 podcast (RSS → mp3 + note; whisper transcribe, desktop), 📺 SRT/VTT
(jimaku), 📺 Plex (live session + library browse), YouTube (history / URL /
bulk), 📕 Kindle highlights + note.com articles, X (search, selection, corpus),
dictionary (35 dicts / 6.4M terms), ⤵ 収集トレイ (drop anything from any app),
分類キャプチャ (classify a selection into the 6-class catalog). Medium coverage
is genuinely broad, and `inbox.ts` already types a mark's medium as
`yt | podcast | tv | manga | book | note | x | web`.

**The problem is not missing doors. It is that there are two roads and they
never meet.**

| | Road A — the tray | Road B — the ⚡ pipeline |
|---|---|---|
| entry | flick anything from any app | capture note w/ `sources:` |
| mediums | all | only what has a transcript in the vault |
| speed | one gesture | four steps |
| produces | catalog entry + attestation | **reconciled card: timestamp, quote, audio clip, deep link** |
| reconciles against the source? | **no** | yes |

Verified by grep: `TrayView.ts`, `inbox.ts` and `reach.ts` contain **no**
reference to `runPipelineOn`, `runFullPipeline` or `reconcile`. There is no road
from the tray to reconciliation. So the fast door produces the weak artefact and
the strong artefact is behind the slow door — which is exactly the friction
being felt, and it is structural rather than a matter of polish.

There *is* a bridge, and it is the thing to build on: `catalog-sweep-transcripts`
(`sweep-match.ts`) takes catalog entries and finds them across every transcript,
writing `status:'suggested'` attestations — class-aware, with inflection
handling. That is tray-content getting reconciled after the fact. But it is a
manual command sitting 38th in a list of 60, it only runs against transcripts
already in the vault, and nothing tells you when it would be worth running.

**The shape of the fix, in order:**

1. ~~**Auto-sweep on drop.**~~ **BUILT 2026-08-01** — `autoSweepEntry` /
   `autoSweepAfterCapture` in `main.ts`, fired from `CaptureModal`'s `onSaved`,
   pinned by `golden/auto-sweep.mjs` (20 checks).

   Measured on this vault (596 notes, 123 transcripts, 103k lines):
   **322 ms on the first drop of a session, ~85 ms warm.** Transcripts are
   cached by (path, mtime), and the *negative* result is cached too — 480 of the
   596 notes are not transcripts and re-reading them was the bulk of the cold
   cost.

   Two design decisions worth keeping straight, both of which fell out of
   measurement rather than taste:

   - **Tier 2 only.** Tier 1's fuzzy `reconcileOne` costs 1.1–4.8 s *per entry*
     across this vault (that is why the full sweep is minutes and never gets
     run). It is also the tier that writes CONFIRMED attestations, which is a
     claim about meaning the project reserves for a human. Everything the
     auto-sweep writes is `status:'suggested'`. A prefilter to make Tier 1
     affordable was tried and **rejected**: it silently lost 2 of 46 real hits
     on 「気になる」, and a sweep that quietly misses attestations is worse than
     one that never claimed them.
   - **Capped at 12, round-robin across files.** 「気になる」 finds 135 sightings
     in 74 files; 「っていうのは」 238 in 96. Writing all of them on one drop would
     bury the ✓✕ queue under a single phrase — the "volume is not evidence"
     failure again. The gesture's job is *discovery*; the manual full sweep
     remains for exhaustive work. The Notice states the total whenever the cap
     bites, so a truncated result can never read as "that is all there is."

### #8 — BUILT 2026-08-01

`src/study/ratify.ts` (pure) + `ratify-store.ts` + the probe surface in
`ReviewView`. `golden/ratify.mjs`, 63 checks.

**One probe per graded card, never a queue.** At the instant a card is graded the
learner has just reconstructed the pattern from memory — the expensive work is
already paid for, so one judgement about that same pattern costs a keystroke
there and a context switch anywhere else. Any key that advanced the card still
advances it; `わからない` is a recorded answer and the question ripens with the
schedule (`MAX_REASKS`).

**Value order: move → class → sighting.** A move claim settles every sighting
behind it; a class decides the matcher, the card shape and sweepability forever;
a sighting settles one occurrence.

**The trap the module is built around.** Asking about the most *uncertain*
candidate is what an active learner wants and is exactly what makes the resulting
precision a lie — an uncertainty-drawn sample is biased low by an unknown amount,
and the naive number would look alarming and be believed. So every row records
**why it was asked** (`pick`), one draw in `MEASUREMENT_EVERY` is uniform, and
`report()` computes precision from the uniform rows *alone*, with a Wilson
interval, refusing to state a percentage below its floor.

**The ledger starts empty on purpose.** 239 confirmed attestations exist and
folding them in would look like a free head start; a confirmed attestation may
have been hand-captured (never a machine claim) or ratified from a queue the user
chose to look at, and neither can be assigned a `pick`. Rows with an unknown
sampling reason cannot enter a proportion — which is the reason the ledger had to
exist.

**The drill answer was already this datum and was being discarded.** Every 予測
question compares a human pick against the calculus's primitive and threw it away
on close. Now recorded as `drill` — *not* parser accuracy, because at a freeze
point a disagreement is usually the learner and there is no third party to say
which. Its use is `drillSplits`: a claim refused the same way repeatedly.

**Measured on the real catalog.** 17,891 suggested attestations against 239
confirmed and 1 rejected — but 28 entries hold 17,823 of them (「ですね」 3,565).
Counted the way `context-tree.ts`'s own doctrine says to, the job is **3,266
questions, not 18,163**: 17 move claims standing for 14,897 sightings, 255 open
classes, 2,994 one-at-a-time sightings. A 20-card session produced 20 probes, 4
of them move claims settling 2,803 sightings between them.

**Two things the real data forced.** (a) A pattern enters the deck only once it
has a *confirmed* attestation, so the 🔴 forms carrying the concordance — all
17 move claims — were unreachable through the card loop; `bestClaimProbe` is the
fallback when a graded card has nothing of its own. (b) Coverage keys on the
claim *existing*, not on it still being open, or answering "「ですね」 marks
agreement" handed its 3,565 sightings straight back as 3,565 questions.
